# thunar

Only `uca.xml` is tracked -- Thunar's **custom actions**, the entries in its
right-click menu. `install.sh` links that one file, never the whole
`~/.config/Thunar/` directory: `accels.scm` lives beside it and Thunar rewrites
it whenever a keyboard shortcut changes.

Thunar also rewrites `uca.xml` itself whenever you edit custom actions in
*Edit -> Configure custom actions*. That means a `git diff` here after using
that dialog is expected, not a bug -- commit it.

## Why "Open Terminal Here" calls kitty directly

The action Thunar ships by default runs:

```
exo-open --working-directory %f --launch TerminalEmulator
```

which fails on this system with *"Failed to launch preferred application for
category TerminalEmulator -- could not find fallback TerminalEmulator
application"*. Nothing is wrong with kitty. `exo-open` hands that category to a
separate binary, `xfce4-mime-helper` (the string is in
`/usr/lib/libexo-2.so.0`), and it is **not installed**: in Xfce 4.20 the mime
helper moved out of `exo` into the `xfce4-settings` package. No `helpers.rc`
entry can fix that, because the program that would read it is missing.

So the action runs `kitty --working-directory %f` instead. Installing
`xfce4-settings` would also have worked, at the cost of ~54 MB once
`elementary-icon-theme`, `colord` and `gnome-themes-extra` come along with it --
not worth it for one menu entry.

**One thing this does not fix:** Thunar's *File menu* has its own built-in "Open
Terminal Here", hardcoded to the same `exo-open` call (`strings /usr/bin/thunar`
shows it), and that one still fails. Use the right-click entry.

## Archives

Handled by `xarchiver` plus `thunar-archive-plugin`, both in
`packages/pacman.txt`. The plugin adds **Extract Here** / **Create Archive** to
the right-click menu; the `xarchiver.tap` file that teaches the plugin how to
call xarchiver ships with xarchiver itself, not with the plugin.

Double-click is separate from the right-click menu: it needs xarchiver
registered as the default handler for each archive type. Stage 8 of `install.sh`
does that with `xdg-mime`, which writes `~/.config/mimeapps.list` -- per-user
state, so it is set by the installer rather than tracked as a file here.

xarchiver is a front end; the real work is done by command-line tools. `unzip`
only *extracts*, so `zip` is in the package list as well -- without it,
"Create Archive" cannot produce a `.zip`. `7z`, `tar`, `gzip`, `bzip2`, `xz`,
`zstd` and `unrar` are already present. Creating `.rar` needs the proprietary
`rar`, which is not installed and is not worth adding -- use `.7z` or `.zip`.

## Thumbnails and the image preview

Thumbnails are generated by **`tumbler`**, a D-Bus service Thunar asks for
pictures. Without it every file gets a generic icon no matter what is in it --
that was the state here, even though tumbler's *plugins* (`ffmpegthumbnailer`
for video, `poppler-glib` for PDFs, `libgsf`) were already installed with
nothing to plug into. `webp-pixbuf-loader` is in the package list too, so `.webp`
is treated like `.png`.

Three xfconf keys turn the rest on. They are per-user state, so stage 8 of
`install.sh` sets them rather than tracking a file:

| key | value | what it does |
|---|---|---|
| `/misc-image-preview-mode` | `..._EMBEDDED` | preview pane inside the window, not a separate one |
| `/last-image-preview-visible` | `true` | the pane starts open |
| `/misc-thumbnail-mode` | `..._ONLY_LOCAL` | thumbnail local disks and USB drives, never a network mount |

`ONLY_LOCAL` rather than `ALWAYS`: `/run/media` counts as local, so the USB
drive is covered, but a future network share will not be pulled over the wire
just to draw icons.

**Game Mode turns this off.** `scripts/power/game-mode.sh` saves the current
thumbnail mode, sets it to `NEVER` and kills `tumblerd` -- opening a folder of
screenshots mid-game then decodes nothing. Turning Game Mode off restores
whatever the mode was before, not a hardcoded default.

## Colours

Two separate things follow the wallpaper.

**Folder icons.** `scripts/theme/folder-colors.sh` runs after every `wallust`
run. Papirus already ships ~25 folder colour sets (`folder-teal.svg`,
`folder-orange.svg`, ...) and plain `folder.svg` is just a symlink to
`folder-blue.svg`, so nothing is generated: the script reads the fill colour out
of each variant, picks the nearest to wallust's accent (redmean distance, so a
dark red and a dark blue are not called "close"), and builds
`~/.local/share/icons/wallust-papirus` out of **symlinks** into Papirus. About a
thousand links, no copying -- Papirus-Dark is 33 MB -- and no root, which is what
`papirus-folders` would need on every single wallpaper change.

The candidate colours are not hardcoded: any `folder-<name>.svg` that also has a
`folder-<name>-documents.svg` is a colour set, so a Papirus update that adds one
is picked up by itself. Special folders (Documents, Downloads, Pictures) and the
home icon are linked too, or they would stay blue while everything around them
changed.

The theme **name** never changes, only its contents, and that is what makes it
live: there is no XSettings daemon under Hyprland, so GTK reads
`gtk-icon-theme-name` once at startup -- but it watches the icon theme's
directory and reloads when the files under it change.

**Window colours.** `wallust/templates/gtk.css` becomes `~/.config/gtk-3.0/gtk.css`:
`@define-color` only -- background, text, list background, selection, borders --
and nothing structural, since a stylesheet that fights the theme's layout is how
GTK apps end up with clipped labels after an update. GTK3 reads it at startup,
so a Thunar window that is already open keeps the old colours until it is
restarted.

**GTK4 / libadwaita apps are not tinted.** They use their own named colours and
ignore `@define-color`; half-doing it would look worse than leaving them alone.
